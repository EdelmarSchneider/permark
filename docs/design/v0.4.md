# v0.4 design: the agent connection

An AI agent working in a project (Claude Code, Cursor, opencode, Codex, Gemini CLI, or a script) can learn what the person
is doing in the project's documents, and can show them a place. In a code editor this link already exists: the agent knows
the open file and the selection, so "explain this" works without pasting. TrailMark gives documentation the same link.

Principles: **off by default, per project**; local only; visible while in use, with an off switch in one click; the agent
reads, and the only things it can do are show a place and mark a review note done. No product feature depends on any one
agent tool.

## 1. What an agent can learn and do

| Tool (MCP) | What it answers / does |
|---|---|
| `get_context` | The open document (path), the mode (reading, Visual, Source), the section on screen (heading path and line range), the selection (text, heading path, line range) when there is one, and whether there are unsaved edits. |
| `list_unread` | Documents changed since the person last read them (the v0.3 unread markers), newest change first, with the time of the change. |
| `search` | "Where is X described?": ranked sections (path, heading path, line, snippet), the same index as Search everywhere. Semantic results join it in v0.5 through the same tool. |
| `list_notes` | Review notes (§3): open ones by default, with path, quoted passage, heading path, line, the note text and its time. |
| `resolve_note` | Marks a note done, with an optional short reply ("Rewritten in 3f2a1c"). The only write an agent can make. |
| `open` | Shows the person a place: a path, optionally a line or a heading. TrailMark opens it in the window without taking focus from the agent's terminal, tints the section, and shows a toast "Opened by an agent · Back". |

Every answer is small and plain (paths relative to the project root, `/` separators), so it fits in an agent's context.
Nothing about other projects, other windows or the file system outside the project is ever exposed.

## 2. How the agent connects

```
 agent (any MCP client) ──stdio──▶ trailmark mcp ──local socket──▶ TrailMark window of that project
                                        │
                                        └── reads .trailmark/local/agent.json when the window is closed
```

- **`trailmark mcp`**: the TrailMark program started with the `mcp` argument runs as an MCP server over stdio (no window).
  Every MCP client supports stdio, so one line of configuration works everywhere:
  `{"command": "trailmark", "args": ["mcp"]}` (Claude Code: `claude mcp add trailmark -- trailmark mcp`). The project is
  the folder the agent runs in (its working directory, or the nearest parent that TrailMark has open or knows).
- **Live link**: the TrailMark process of that project listens on a local socket (a named pipe on Windows, a Unix socket in
  the account's runtime folder elsewhere), reachable only by the same account. The socket exists only while the connection is on.
  Messages are JSON lines; the MCP layer (Rust SDK `rmcp`) only translates.
- **Window closed**: `get_context` answers that TrailMark is not open; `list_unread`, `list_notes` and `search` still work
  from the files on disk (`read.json`, notes, and a fresh section index built by the `mcp` process); `open` starts
  TrailMark on the project.
- **State file for anything else**: while connected, the app also writes `.trailmark/local/agent.json` (the `get_context`
  answer, updated at most every 300 ms), so a shell script or a tool without MCP can read where the person is. Only in
  projects that keep their state in `.trailmark/` (Initialize TrailMark); the `mcp` process finds the AppData location by itself.
- **`trailmark context`**: prints the context as one short paragraph and exits. Recipe (documented, never required): a
  Claude Code `UserPromptSubmit` hook that runs it, so every prompt carries "Viewing docs/plan.md › Rollout (lines 40-62),
  selected: '…'". Other tools can do the same with their own hooks.
### Spike result

`trailmark mcp` works from the TrailMark program itself; no second program (console sidecar) is needed, and the
configuration line stays `{"command": "trailmark", "args": ["mcp"]}`.

- **Windows release build.** It is a GUI program (no console of its own), and an MCP client that starts it with piped
  standard input and output gets normal answers: the first reply arrives within about 10 ms, no window or console appears
  (a console program started by a GUI client can flash one), and the program exits within a few milliseconds of the input
  closing, or when the client dies without saying goodbye. Checked with a raw JSON-RPC client in Node (`initialize`,
  `notifications/initialized`, `tools/list`, `tools/call ping`), with standard error piped, ignored and inherited, and
  through a `cmd /c` wrapper.
- **SDK.** `rmcp` 3.5 (the official Rust SDK) with its stdio transport and tool macros. It adds about 1 MiB (8 %) to the
  program (13.4 MiB against 12.4 MiB for the Windows release build).
- **Start-up rule.** The program serves MCP when `mcp` is its first argument; any other start opens the window as before.
  Standard output carries only protocol messages; a failure goes to standard error with exit code 1.
- **Terminals.** Writing to a terminal is the one thing a Windows GUI program cannot do by itself. `trailmark context`
  (above) will attach to the terminal it was started from when its output is not redirected; an agent's hook captures the
  output through a pipe and is unaffected.
- **Tests.** The MCP round trip runs in-process over an in-memory pipe, and the real program is started with piped streams
  on every platform in CI.

## 3. Review notes

A person reading can leave a note on a passage ("this contradicts §2", "simplify"), then ask the agent to "go through my
notes". Useful for any document, not only specs.

- **Add**: select text in the reading view → the selection popover gets **Note** (also `N` with a selection). A small
  field opens under the passage; Enter saves, Esc cancels.
- **Anchor**: path + quoted text + heading path + line range at the time. When the document changes, the note re-anchors
  by its quote (then by heading, then by line); a note whose passage is gone is shown as "passage changed" in the list,
  never silently dropped.
- **See**: a thin accent bar in the margin next to the passage (click → the note), and a **Notes** tab in the right panel:
  open notes of the project grouped by document, done ones folded; each row jumps to the passage. Status bar: "3 notes".
- **Done**: by the person (check on the row) or by the agent (`resolve_note`, with its reply shown under the note).
- **Stored** in `.trailmark/local/notes.json` (or the AppData state folder): personal by default, never committed. Sharing
  notes with a team (a committed file) is a later option.
- Notes work without the agent connection; the connection only lets an agent read and resolve them.

## 4. Turning it on, and seeing it

- **Settings → Agent connection** (per project): off by default. Turning it on shows the configuration line with a Copy
  button, for Claude Code, for other MCP clients (JSON), and the `trailmark context` recipe.
- **Status bar**: while on, an item "Agent" with a dot: hollow when nothing is connected, filled while an agent is
  connected, with a short pulse when it reads or opens something. Click → popover: what is shared (the list of §1),
  the last few requests ("get_context · 10 s ago", "open docs/plan.md · 2 min ago"), and **Turn off**.
- **Command palette**: "Agent connection: turn on/off", "Copy agent setup".
- Turning it off closes the socket and deletes `agent.json`; the `mcp` process then answers that the connection is off
  and how to turn it on.

## 5. Build order

1. Spike: `trailmark mcp` over stdio from the release build on Windows (or the sidecar), `rmcp`, one `ping` tool.
2. Core: per-project setting, local socket, context publishing from the UI (debounced), `agent.json`, `get_context`,
   `list_unread`, `search`, `open`, `trailmark context`. Tauri-free modules with tests; an MCP round-trip test.
3. Status bar item, popover, Settings section, setup snippets.
4. Review notes: anchoring (pure, tested), store, selection popover, margin bars, Notes tab, `list_notes`, `resolve_note`.
5. README section "Use with an AI agent" (Claude Code, Cursor, generic MCP, hook recipe).

## 6. Decisions

- Notes are personal (local) by default; shared notes later.
- An agent may resolve notes but not create them or edit documents.
- `open` never takes focus; the person looks when they want (toast + tint).
- The selection text is shared while the connection is on (it is the point of "rewrite this"); there is no separate switch.

## 7. How the connection works (build steps 2 and 3)

What the tools do, and the rules that keep them safe. Every limit named here is one constant in the code.

### The project and the setting

- The setting is **Agent connection** in the project's saved session, off until it is turned on. A project that keeps
  its state in `.trailmark/` keeps it in `.trailmark/local/session.json`, otherwise it is in the app's data folder.
  A single file (Simple mode) has no project and no connection.
- `trailmark mcp` and `trailmark context` find the project from the folder they run in: the nearest folder above it
  that has a `.trailmark/` folder, or that the app has kept state for (that is, a folder that was opened in
  TrailMark). They read the setting each time a tool is called, so turning the connection on or off takes effect
  while an agent is running. In a folder TrailMark has never been used on, every tool says so.
- With the connection **off** (or not set up), every tool answers `status: "off"` and says how to turn it on
  (Settings > Agent connection, or the command palette).

### The local socket

- One socket per project and user. On Windows it is a named pipe, `\\.\pipe\trailmark-<id>`, whose access list lets
  in only the owner of the pipe; the first instance is exclusive, so another program cannot take the name first. On
  Linux and macOS it is a Unix socket `<id>.sock` in a private folder (mode 0700) inside the user's runtime folder
  (`$XDG_RUNTIME_DIR`) or a per-user folder in the temporary folder; a folder that is not the user's, or a link in its
  place, is refused. `<id>` is a hash of the project's key and the user's name, so both sides find it without a
  registry. The socket exists only while the connection is on and the window is open on the project.
- Messages are JSON lines, one request and one reply each, with an `id`; a request line over 64 KiB closes the
  connection. `trailmark mcp` keeps one connection for its whole life, which is what the status bar shows as "an
  agent is connected".
- The crate is `interprocess` (local sockets with Tokio on both systems, and a safe way to give a named pipe an
  access list). Standard library sockets cover only Unix; Tokio alone would need unsafe code for the Windows access
  list, and the crate denies unsafe code.

### The tools

| Tool | With the window open | With the window closed |
|---|---|---|
| `get_context` | the latest message the window published | `notOpen`: "TrailMark is not open on this project." |
| `list_unread` | the live unread markers | worked out from `read.json` and the files |
| `search` | the live index (the one Search everywhere uses) | a section index built from the files, kept up to date |
| `open` | the window opens the place | TrailMark is started on the project (and shows it once it is up) |

- Paths are relative to the project with `/` separators; nothing outside the project is ever listed, found, shown
  or opened. A document in a linked worktree lives outside the project folder, so it is left out of every answer.
  The window's word is not trusted for a path: what it publishes is checked against the project before it is kept.
- `search` returns plain text snippets (no markup), at most 25 sections (10 when not asked). `list_unread` lists at
  most 200 documents, newest change first, with the time of the change.
- `open` takes a path and optionally a line or a heading (`Rollout`, or `Plan > Rollout`); a heading wins over a line
  because it survives edits. A heading the document does not have is reported, and the document opens at its top.
  When TrailMark is closed, `open` starts it and waits up to 25 seconds for it to listen. A person who is editing is
  not taken away from their work: a notice offers the place instead.
- The tool descriptions say when to call each one ("this", "here", "the selected text" for `get_context`).

### What the window publishes

The window sends the message 300 ms after anything it depends on changes: the open document, the mode (reading,
Visual, Source), the section on screen (heading path and lines), the selection (text, heading path and lines),
and whether there are unsaved edits. A selection is cut at 4,000 characters and says so. In the reading view the
selection's lines are those of the blocks it touches; in Source they are exact; in Visual the editor cannot tell, so
there are no lines. While the connection is on and the project keeps its state in `.trailmark/`, the same message is
written to `.trailmark/local/agent.json` at most every 300 ms and deleted when the connection is turned off or the
project is closed. A window that is killed leaves the file behind; it is removed the next time the project opens with
the connection off, and `updatedAtMs` (milliseconds since the Unix epoch) tells a reader how old it is.

`trailmark context` prints the message as one paragraph, for a hook:

```
Viewing docs/plan.md › Plan › Rollout (lines 40-62), selected (lines 44-46): 'ship it on Friday'.
```

When there is nothing to say (the connection is off, or TrailMark is not open) it prints nothing on standard
output, explains on standard error and exits with 0, so a hook adds no noise to a prompt. A GUI program on Windows
has no console of its own: the output goes to a pipe, which is what a hook uses; in an interactive terminal pipe it
through `more`.

### The status bar, the popover and the setup lines

- **Agent** appears in the status bar while the connection is on: a hollow dot when nothing is connected, a filled
  one while an agent is, and a short ring when it asks something (a still ring with reduced motion). Clicking it opens
  what is shared, the latest requests ("Searched for rollout plan · just now"), **Set up an agent...** and **Turn off**.
- Settings > Agent connection has the switch and, while it is on, the lines to copy: Claude Code
  (`claude mcp add trailmark -- <program> mcp`), the JSON every MCP client takes, and a Claude Code
  `UserPromptSubmit` hook that runs `<program> context`. `<program>` is the path of the running program, quoted for
  the line it is in (the AppImage file for an AppImage): `trailmark` is not on the PATH after an install on Windows
  or macOS, so the bare name would not work.
- The command palette has "Agent connection: turn on", "Agent connection: turn off" and "Copy agent setup" (the JSON).
- The window shows a place an agent asked for without taking focus: the document opens, the section is tinted, and a
  notice reads "Opened by an agent" with **Back**.

### The choices of section 6, as built

Each is one line to change: notes are the person's and stay local (section 8); an agent can show a place and mark a
note done, and nothing else; `open` never raises the window; the selection is shared with the connection and has no
switch of its own (`MAX_SELECTION_CHARS`).

## 8. Review notes, as built (build step 4)

### What a note keeps, and where

A note belongs to the person, not to the document. `notes.json` sits beside `read.json`, in `.trailmark/local/` for a
project that keeps its state there and in the app's data folder otherwise (Initialize carries it over). It is never
committed. Each note holds the document, what the person wrote, the passage they selected, the few words just before
and after it, the headings above it, its lines, the time, and, once done, who finished it, when, and an agent's reply.

- The file is rewritten atomically, and **every change reads it again first**, so the window and `trailmark mcp` can
  work on the same file without overwriting each other. A file that cannot be read (damaged, or written by a newer
  version) is set aside as `notes.unreadable-<time>.json` and a new one is started; the person's words are never
  deleted by the program.
- Limits, each one constant in the code: a quote of 1,000 characters (the start of a longer selection is what is found
  again), a note of 2,000, a reply of 1,000, 5,000 notes in a project, 200 listed to an agent.
- A single file (Simple mode) has no project and takes no notes. Notes need a Markdown document.

### Finding the passage again

When a document changes, a note is found again by its quote, then by its heading, then by its line, and it is never
dropped.

1. **The quote.** The document is turned into what a reader sees (formatting, link addresses, list markers and raw tags
   are gone) and then into its letters and digits, in lower case. The quote is turned the same way, so a selection taken
   from the reading view matches the source behind it: `**bold**`, a link's text, smart quotes, line breaks and table
   cells all compare equal. Where the words occur more than once, the words around the note decide, then the nearest
   line to where it was. The lines of a note are those of the blocks the quote touches (a paragraph, a list item, a table
   row, a code block).
2. **The heading.** If the quote is gone, the note points at the section it was in: the same headings, else the section
   with the same last heading (so a section that moved under another heading is still found).
3. **The line.** If that is gone too, the line the note was on, kept inside the document.

A note found by its quote is **anchored**. One found by anything else is shown as **Passage changed**, with the place it
points to; one whose document is gone is **Document missing**, and comes back to life if the document does. When the
window lists the notes, the places that moved are written down, so a later rewrite still finds its way back to the
right section. A listing for an agent while the window is closed reads only and writes nothing.

A Markdown file renamed or moved in the Explorer takes its notes along (a folder takes everything in it); a rename made
by another tool leaves the notes on the old name, marked **Document missing**.

### In the window

- **Add**: the selection toolbar has **Note** (`N`); a small field opens under the passage, which stays highlighted
  while the person types. `Enter` saves, `Shift+Enter` starts a new line, `Esc` cancels. Clicking elsewhere closes the
  field only while it is empty, so a note being written is not lost. From the command palette, **Add a note to the
  selection** uses the selection from the moment before the box opened.
- **See**: a thin accent bar in the right margin beside the passage of each open note (the live-change bar uses the
  left), spanning the innermost blocks that hold it; a click shows the note in the Notes tab. Done notes and notes whose
  passage changed have no bar.
- **Notes tab**: open notes grouped by document in path order and by line, each row with the quoted passage, the note, its
  section, line and age; a click goes to the passage; the check marks it done; the done ones sit under a fold with their
  documents named, the agent's reply under its note. A small button deletes a note. The status bar says "3 notes"
  while any are open, and opens the tab.
- The list is asked for again when the backend says it changed, a moment after a document is drawn again (opened, saved,
  changed by someone else), and when a file with notes changes on disk.

### The tools

| Tool | Arguments | Answer |
|---|---|---|
| `list_notes` | `which`: `open` (the default), `done` or `all` | `notes` (by document and line, at most 200), `total`, and `source`: `window` or `files`. Each note: `id`, `path`, `quote`, `headingPath`, `line`, `endLine`, `text`, `created`, `state` (`anchored`, `passageChanged`, `documentGone`), `done`, and, once done, `doneBy`, `doneMs`, `reply` |
| `resolve_note` | `id`, optional `reply` | The note as it is now, in `note`, and `source`. Resolving a note that is done already keeps who did it first and adds the reply |

Both answer `status: "off"` with the connection off, like every other tool, and both work with the window closed, on the
same file. Notes in a linked worktree's documents are left out, like everything outside the project folder. The status
popover lists the two among what an agent did.

### Known limits

- A passage that includes text the app draws itself (the label of a code block, a diagram's labels, rendered math) may
  not be found in the source; the note is kept and says **Passage changed**.
- A note on one line of a list item that holds a nested list gets a bar as tall as the item's own text, not the list.
